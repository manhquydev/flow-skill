# ADR 0002 — Unattended npm release policy

## Status

Accepted for implementation; live publishing remains disabled until exact-HEAD review/CI, a verified default-off dry-run, configured `FLOW_AUTOPUBLISH_ENABLED`, and a runner-provided `gh >=2.68.0` attestation verifier are confirmed. This repository currently has no OMP App installation requirement; `release.sh` uses the existing authenticated `gh` caller ID and binds it to the returned publisher run.

## Owner objective

The existing OMP product loop prepares a backwards-compatible release PR, waits for required review and authoritative master CI, then invokes the canonical `bash scripts/release.sh --yes` path. That script dispatches one publisher workflow for the exact master SHA and npm package version. Release intent explicitly selects the axes: `npm_version` is required for publication; `skill_version: null` means the skill product is unchanged and requires no new skill tag/Release; a non-null skill version requires its matching changelog and tag/Release. Prereleases publish to `next`; stable versions publish directly to `latest`. No release occurs for a loop tick without a committed version/changelog change. Breaking compatibility or expanded service/security rights requires a separate owner decision.

## Context and verified environment boundary

Flow owns gates and receipts, never the runtime (ADR 0001). OMP remains the orchestrator; GitHub Actions performs a bounded publisher job only after an explicit `release.sh` dispatch. There is no autonomous CI `workflow_run` promotion entry and no tag-push publish trigger. `release.sh` captures the existing authenticated caller ID via `gh api user`, includes it in the request, and validates the returned exact run ID and actor. This is traceable same-owner authorization, not an independent identity boundary.

Controller-authorized Stage 1 remote change/readback (2026-10-19): `npm-publish` deployment policy is `{protected_branches:false, custom_branch_policies:true}` with exactly one rule `{type:branch,name:master}` and no tag/wildcard rules. Old tag-selected workflow probe run `39210527539` at tag `npm@0.7.11` / old YAML ref `e69171c` was rejected before job execution: publish job `117922661201` had zero steps; GitHub annotation said the tag was not allowed by environment protection. Evidence: `.omp/flow-maintenance/backups/release-remote-20261019T055718Z/`. No npm trusted-publisher/account setting or master ruleset change was made by Stage 1.

## Decision

1. Retire the `push: tags: npm@*` publisher entry. A tag is output of successful release, never authorization to publish.
2. Use `workflow_dispatch` as the only publisher trigger. Required inputs include mode (`dry-run` default; `publish` only from release.sh), full expected master SHA, npm version and unique dispatch UUID. `release.sh` calls GitHub's workflow-dispatch REST endpoint with `return_run_details=true` and `X-GitHub-Api-Version: 2022-11-28`; it validates the returned repository-bound `workflow_run_id`, then watches and re-reads that exact run. Missing/204/invalid details fail closed without retrying the dispatch. Dispatch ref must be master; no latest-run/actor/time polling. Workflow uses non-cancelling concurrency.
3. Publisher eligibility job is least-privileged and has no `npm-publish` environment or `id-token:write`. It independently verifies exact remote/check-out SHA, package and skill versions/changelogs, merged PR to this repository's master, latest successful authoritative CI workflow/run/attempt and exactly one successful `all-checks-passed` job, channel monotonicity, and registry absence. It fails closed on API pagination/incompleteness, auth/network/schema errors, and treats only explicit E404 as absence.
4. Publish job requires `mode=publish`, `FLOW_AUTOPUBLISH_ENABLED=true`, and eligibility success; it alone uses `npm-publish` and OIDC. Missing/false variable skips live publishing. Keep it false until the implementation is reviewed and exact-HEAD CI plus a no-publish workflow dry-run pass. The controller may activate it under the existing owner authorization once those concrete gates pass. No additional GitHub App/account is required or requested.
5. Immediately before publish, re-read master/CI/registry and verify the pack artifact belongs to exact SHA/version/workflow run. Pack once because `sync.mjs` writes nondeterministic `syncedAt`; publish that exact tarball. Never re-pack to resolve an ambiguous publish.
6. After publish, verify registry version, tarball SHA-512 SRI, provenance subject, dist-tag and installed behavior via `npm-wrapper/scripts/smoke.mjs <version>`. Provenance must be present and correct; legacy warning-only behavior cannot authorize the new release.
7. Existing npm versions are never republished. Recovery is verify-only: `release.sh` may proceed only when it has the retained exact tarball and verifies registry SHA-512 integrity, npm `audit signatures` output and GitHub Sigstore SLSA identity/source fields, channel, exact tags and GitHub Release target. If the retained tarball or installed `gh attestation verify` is unavailable, stop with owner action; do not overwrite, unpublish, move tags, or silently repair.
8. `release.sh --yes` preserves local cleanliness, dual-axis coherence, exact master SHA/CI, unused tags, no-drift, i18n and read-only battery gates. It dispatches at exact SHA/version with a unique UUID, uses the API-returned run ID rather than heuristic list polling, verifies that run's workflow/path/ref/SHA/event/title/conclusion, and requires exactly one successful eligibility job plus exactly one completed-success publish job on that run attempt. It verifies npm registry/provenance/smoke before creating/pushing Git tags and GitHub Release. Missing dispatch details are not blindly retried. It never mutates remote environment/variable settings. Dry-run dispatch does not receive OIDC and must report the publish job as skipped.
9. Third-party GitHub Actions in the privileged workflow are pinned to verified full commit SHAs. No shell interpolation of untrusted dispatch inputs; pass through environment and validate full SHA/SemVer.

## Required acceptance evidence

- Unit/fixture coverage for exact workflow/run/job/attempt, PR response shapes/base repo, no intent, changelog/version mismatch, SemVer precedence, channel downgrade, E404 vs 403/429/5xx/timeout, exact existing reconciliation vs mismatches, pack integrity/run binding, pre-publish master/registry race, dry-run/default-off/no-OIDC, dispatch SHA/version mismatch, absent/wrong provenance, install smoke failure, and partial tags/releases with no mutation.
- Workflow contract checks prove no tag trigger; dispatch is master-only; dry-run is default and cannot reach publish; live job requires latch + eligibility + environment and alone receives OIDC; immutable action pins; pack-once and exact archive publish.
- `release.sh` must prove dispatch targets current exact master SHA/version, waits for the matching publisher workflow run, fails closed on timeout/non-success, and creates tags only after installed artifact verification.
- Independent review of the actual implementation diff; surface-matched tests and exact-HEAD PR CI. Keep the enable variable false until reviewed implementation, exact CI, positive dry-run/no-op and controller readback succeed. Then controller enables it under the existing owner authorization and verifies one meaningful release end-to-end.

## Residual and rollback

Same-owner credentials can modify workflow, variable and environment. OIDC/SLSA provides traceability, not protection from owner compromise; this is not an independent identity boundary. Dispatch authorization is correlation-based by accepted policy: the caller-supplied actor ID and dispatch UUID bind the run to its caller for traceability, they do not — and are not intended to — prove that only `release.sh` invoked the workflow. Any authorized same-owner credential may dispatch; the enforced boundaries are the server-side gates: the default-off `FLOW_AUTOPUBLISH_ENABLED` latch, the master-only `npm-publish` environment, exact-HEAD CI/merged-PR/intent/registry eligibility, and OIDC provenance binding. To pause, controller sets the enable variable false or disables the dispatcher; do not unpublish versions or move/delete release tags. Do not change the ruleset or npm trusted publisher as part of this implementation.

## Unified-version amendment — 2026-10-25

The [owner decision](../release-owner-decision-unified-version.md) replaces dual-axis version separation with one common skill/npm SemVer. An existing immutable skill tag may be reused only after its origin ref is proven present and stable and its `skills/` tree matches the release revision. Ship compares HEAD; retained-artifact reconciliation compares the provenance-bound retained commit, never a later checkout. Missing or different remote content fails closed. npm tags still require the exact retained release SHA; no existing tag is moved.
